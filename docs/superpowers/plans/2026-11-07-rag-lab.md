# RAG Lab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Customers upload a knowledge base, build indexes with the commonly used chunking and retrieval methods, run the same prompt-agent scenarios without RAG, with full-context stuffing, and with up to 4 RAG configs, then read a report of retrieval quality, hallucination, latency, cost and savings, plus a recommendation.

**Architecture:** RAG is a property of a prompt version (`prompt_versions.rag_config`) and can be overridden per run (`test_runs.config["rag"]`). Indexes are immutable, versioned builds made by a new `indexer` Kafka worker, in the same pattern as scenario generation. The text runner retrieves before each agent turn and records a `retrievals` row per turn. The evaluator gains a second step that writes `rag_metrics` per call. A "RAG matrix" is a record that groups one ordinary run per config/baseline, so planner, compare and sinks are unchanged. The report aggregates those runs.

**Tech Stack:** as phase 1, plus `fastembed` (ONNX local embeddings and reranker, no PyTorch) and `pypdf`. numpy is already installed.

**Spec:** `docs/superpowers/specs/2026-11-06-prompt-and-rag-testing-design.md` (goals 7–9, "Settled details", "Ground truth"). Builds on phase 1 (`docs/superpowers/plans/2026-11-06-prompt-testing-phase1.md`, PR #11).

## Global Constraints

- New dependencies: only `fastembed>=0.9.1` and `pypdf>=7.0.0`, verified on PyPI on 2026-11-07. Add them to BOTH `backend/pyproject.toml` and the pip line in `backend/Dockerfile`.
- Local defaults:
  - embeddings `intfloat/multilingual-e5-large` (dim 1024, MIT)
  - reranker `BAAI/bge-reranker-v2-m3-int8` (Apache-2.0)
  - Do not use `jinaai/jina-reranker-v2-base-multilingual` (non-commercial licence).
- Models download once to `FASTEMBED_CACHE_PATH`, default `/data/models`, which lands under the existing `./data/runtime` bind mount.
- Every hosted provider HTTP call goes through `pareeksha.agent_llm.base.post_json`. That gives SSRF pinning, no redirects and a 10 MiB cap. Never call httpx directly.
- **Local-only rule.** One guard module, `pareeksha/rag/guard.py`, is the only place that decides it. When `knowledge_bases.local_only` is true:
  - Embedding and reranker providers must be `local`.
  - The model under test must be a local endpoint (`is_local_endpoint`).
  - The platform LLM (DeepSeek/Gemini) never receives KB text: question generation from the KB is refused, and LLM-judged RAG metrics are skipped with reason `local_only`.
- Secrets (embedding/reranker API keys) are write-only, Fernet-encrypted on `knowledge_bases.secrets_encrypted`, and handled exactly like `agents.adapter_secrets`.
- All new tables are tenant-scoped by `project_id`. Every lookup filters by project, and by the parent id where one exists.
- Do not modify `backend/pareeksha/llm/base.py` (frozen); judge calls use `LLMPurpose.JUDGE`. Do not modify `docs/schema.sql` or `alembic/sql/0001_initial.sql`.
- Upload limit: 10 MiB per file (reuse `MAX_UPLOAD_BYTES`), at most 200 documents per KB, and 2,000,000 extracted characters per KB.
- Checks stay green: ruff, format, mypy, backend tests, contract tests (except the 3 known container-only failures), web tsc, lint and Playwright, and the SDK tests.

## Deviations from the spec (designer's calls, recorded here)

- **The matrix is a group of runs, not one run with a config dimension.** `run_items` keeps its unique key, and the planner and compare are unchanged. Comparing any two configs is the existing `GET /runs/compare`.
- **RAG metrics live in their own `rag_metrics` table, not the rubric.** This leaves judge calibration (`rubric-2026-10-v1`) untouched.
- **BM25 runs in-process** (pure Python, Indic-aware tokenizer) rather than Postgres FTS.
  `# ponytail: in-memory per index, move to tsvector/pgvector when a KB exceeds ~50k chunks`
- **Prices are not seeded.** Local models cost 0. Hosted prices are entered per project (`price_overrides`), and the report shows tokens always and ₹ only for priced models. We are not confident of current list prices, and a wrong seeded price is worse than a blank one.

## Review Focus

1. **Malicious or broken uploads** (zip-bomb docx, encrypted or garbage PDF, 9 MB of one line, wrong extension) → 422 `unsupported_document` or `extraction_failed`, never a worker crash or a hang. Extraction has a 30 s time limit and the 2M-char KB cap. (Task 2 tests.)
2. **Local-only KB with a hosted embedding, reranker, agent model, or KB question generation** → refused with error `local_only`, at index build, run/matrix creation, call start and question generation. (Task 4/5/8 tests through the one guard.)
3. **Index not ready, failed, or from a different chunking/model than the config** → run/matrix creation returns 409 `rag_index_missing` listing what to build; never a silent fallback to another index. (Task 9 test.)
4. **Ground-truth quote not found in the document** → that CSV row or generated question is reported as `unmatched`, never stored with a wrong span. (Task 8 test.)
5. **Full-context baseline larger than `context_char_limit`** → the baseline is marked `n/a` with the numbers in the matrix and report, never truncated. (Task 9 test.)

### Task 3: Chunking and search (pure, no I/O)

**Files:** Create `backend/pareeksha/rag/chunking.py`, `rag/bm25.py`, `rag/search.py`, and tests `backend/tests/unit/rag/test_chunking.py`, `test_bm25.py`, `test_search.py`.

**Produces:**
- `Chunk(text: str, start: int, end: int, parent_start: int, parent_end: int)` (frozen dataclass; `text == doc[start:end]`).
- `chunk_document(text: str, cfg: ChunkingConfig) -> list[Chunk]`:
  - `fixed`: windows of `size` chars with `overlap`, snapped back to the nearest whitespace within 10% of the window.
  - `recursive`: split on markdown headings, then blank lines, then sentence ends (`. ! ? । ॥` followed by space or newline), then whitespace. Pack pieces up to `size` and carry `overlap` chars.
  - `sentence_window`: one chunk per sentence, whose parent span is ±`window` sentences.
  - For fixed and recursive, the parent is the enclosing heading section, or the paragraph when there are no headings. It is used by small-to-big.
  - No empty chunks, and offsets are exact.
- `tokenize(text: str) -> list[str]`: lowercase, then `re.split(r"[\s\.,;:!?\"'()\[\]{}<>/\\|\-–—।॥]+")`, dropping empties. Indic matras must stay inside the token.
- `class BM25(docs: list[list[str]], k1=1.5, b=0.75)` with `.scores(query_tokens) -> list[float]`.
- `search.py`:
  - `dense_scores(query_vec: np.ndarray, matrix: np.ndarray) -> np.ndarray` (cosine, normalised).
  - `top_k(scores, k) -> list[tuple[int, float]]`.
  - `rrf(rankings: list[list[int]], k=60) -> list[tuple[int, float]]`.
  - `mmr(query_vec, matrix, candidates: list[int], k, lam) -> list[int]`.

- `read_spec` puts into `AgentTarget.adapter_config["rag"]`:
  - `{config, index_id, kb_id, local_only}`, plus the decrypted KB secrets in `adapter_secrets` (`embedding_api_key`, `reranker_api_key`).
  - For full_context: the KB text concatenated with `"\n\n# <filename>\n"` headers, sorted by filename.
- `class Retriever` (built once per call):
  - `async retrieve(query: str, *, chat: ChatProvider | None) -> RetrievalOutcome(results: list[dict], context: str, queries: list[str], timings: dict, usage: dict)`
  - The index is loaded once per process into an LRU of 8: chunk texts and offsets, a float32 numpy matrix, a BM25 instance, and the document texts for small-to-big.
  - Methods:
    - `bm25`: BM25 top_k.
    - `dense`: embed the query, cosine top_k.
    - `hybrid`: RRF of BM25 and dense candidate_k, then top_k.
    - `hybrid_rerank`: hybrid candidate_k, rerank, top_k.
    - `mmr`: dense candidate_k, then MMR top_k.
  - Query transforms:
    - `multi_query`: one chat call asks for 3 rewrites as a JSON list. Retrieve for each plus the original, then RRF.
    - `hyde`: one chat call writes a short hypothetical answer, which is embedded for the dense part.
  - `small_to_big`: context uses `doc[parent_start:parent_end]`, de-duplicated by parent.
  - Context format: `"[1] (source: <filename>)\n<text>\n\n[2] …"`.
- **text_runner:**
  - Before the first chat call of each agent turn, when rag mode is `retrieval`, retrieve on the caller utterance.
  - The system message for that turn is the version's system prompt with `{{context}}` replaced when present, else the prompt + `"\n\nRetrieved context:\n" + context`. No extra instructions are added.
  - `full_context`: the same placement, with the whole KB text once.
  - Record a `RetrievalRecord(turn_idx=<agent turn idx>, …)` and event `retrieval` `{total_ms, n_results}`.
  - A retrieval failure → event `retrieval_failed`, and the turn proceeds without context. It does NOT end the call; the metric shows it.

### Task 7: RAG metrics in the evaluator

**Files:**
- Create: `backend/pareeksha/rag/metrics.py`, `backend/pareeksha/llm/prompts/rag_judge_v1.j2`, tests `backend/tests/unit/rag/test_metrics.py` and `backend/tests/integration/test_rag_metrics_eval.py`
- Modify: `backend/pareeksha/evaluation/handlers.py` (after `save_evaluation`, ~:76), `evaluation/pg_stores.py` (store methods `load_rag_inputs(call_id)` and `save_rag_metrics(call_id, record)`, an idempotent upsert), the `EvaluatorStore` Protocol, and the fakes in `tests/unit/evaluation/fakes.py`

**Produces:**
- `load_rag_inputs` returns None unless the call's run has a rag config (any mode, including `off` set by a matrix baseline) or the call has retrievals. It returns `RagInputs(mode, retrievals, expectation: RagExpectation | None, source_text: str | None  # doc[span], local_only, agent_turns)`.
- Retrieval metrics are deterministic and only computed with an expectation that has a span. A retrieved result is a hit when it has the same document_id and `[start,end)` overlaps `source_span`:
  - `hit_at_k` (bool)
  - `reciprocal_rank` (1/rank of the first hit, else 0)
  - `context_precision` (hits / results)

  They use the first agent turn's retrieval, which is the answer turn.
- Generation metrics come from one JUDGE `generate_json` call per call, template `rag_judge_v1.j2`, schema `RagJudgeOutput{claims: [{text, supported: bool, evidence: int | null}], answer_correct: bool | null, refused: bool}`. Evidence is the retrieved context (retrieval/full_context modes) plus `source_text` when available; the answer is the agent turns.
  - `faithfulness` = supported/total claims. It is only for retrieval/full_context, and 1.0 when there are no claims.
  - `hallucinated` = any unsupported claim. It is computed for every mode when evidence exists, including no_rag with a ground-truth span.
  - `answer_correct` = from the judge, when `reference_answer` is set.
  - `refusal_correct` = `refused` when `answerable` is false, and `not refused` when it is true.
  - `local_only` → every LLM metric goes into `skipped` with reason `local_only`. No evidence → `skipped` reason `no_evidence`.
- The handler calls `await evaluate_rag(...)` between `save_evaluation` and the `EvaluationCompleted` build. A judge failure records `skipped` reason `judge_error` and never fails the evaluation.

**Produces:**

  - `label, kind, run_id, run_status, n_calls, n_questions_with_truth`
  - `retrieval: {hit_rate, hit_rate_ci: [lo, hi] (Wilson 95%), mrr, context_precision}`
  - `generation: {faithfulness, hallucination_rate, hallucination_ci, answer_correct_rate, refusal_correct_rate, skipped: {reason: count}}`
  - `latency_ms: {retrieval_p50, retrieval_p95, embed_p50, search_p50, rerank_p50, rewrite_p50, turn_p50, turn_p95}`, where turn latency is agent turn `end_ms - start_ms`

  - `index_one_time: {input_tokens, cost_inr | null}`
  - `monthly_cost_inr`
  - `savings_vs_full_context: {inr, pct} | null` and `savings_vs_no_rag: {inr, pct} | null`

Rule: among config rows with `n_questions_with_truth >= 10` and `hit_rate >= 0.7`, take the highest faithfulness, then the lowest cost, then the lowest retrieval_p50. With no eligible row, the reason states why: "not enough ground-truth questions (N < 10)" or "no config reached 70% hit rate". The report always states `n` per row.

  - Local models are always 0.
  - Prices are not seeded (see Deviations).
